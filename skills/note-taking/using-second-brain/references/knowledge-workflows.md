## Capture and triage

**Capture is intake; triage decides what happens next.** A saved link can remain unread. Preserve enough context to return to it; do not fabricate a summary from its title. Respect a request to keep something even if its future use is unknown.

For discretionary selection, look for a recurring question, a surprising observation, a useful example, a lesson from work, or a relevant interest. Add a short “why saved” when known. If the user’s reason is unknown, leave it unknown instead of guessing their motivations. Capturing a thought should not become an interview.

For an authorized inbox-processing task, use a manageable batch and distinguish these outcomes:

| Material | Useful disposition |
|---|---|
| Commitment or actionable request | Link to an existing task; otherwise record an actionable draft or create a task only in the authorized system. |
| Support for a current outcome | Link to the project’s existing hub or support record. |
| Ongoing responsibility or useful interest | Route to the existing area/resource navigation. |
| Reusable idea | Develop only if there is enough substance and benefit now. |
| Interesting but not understood yet | Keep a pointer in intake/reading queue with uncertainty visible. |
| Possible future commitment | Put in the workspace’s deferred/Someday convention, separate from active work. |
| Duplicate, obsolete, or irrelevant item | Identify the existing record or propose archival/deletion; act only under the established permission scope. |

Separate **knowledge from commitments**: supporting evidence belongs in notes; task state belongs in the designated task system. Capture known owner, a verb-led next action, and a genuine due date if given. Do not invent deadlines or contact people because a note says “follow up.” If the task adapter is unavailable, retain a clearly unsynced action draft and report the gap.

Prefer small repeated processing sessions over an indefinite reading backlog. A review may finish its selected batch while leaving an explicit queue. Do not call the entire inbox processed when only a sample was handled.

## Organize by use

Use PARA as a placement heuristic when useful, not a compulsory physical layout:

| Role | Test | Example |
|---|---|---|
| Project | What observable outcome lets us finish? | Publish the onboarding guide. |
| Area | What ongoing standard must be maintained? | Maintain developer onboarding quality. |
| Resource | What topic or interest may be reused? | Examples of good documentation. |
| Archive | What is inactive but worth retaining? | Last year’s completed onboarding redesign. |

A project can have a real timeframe; an unknown deadline stays unknown. For a note useful in multiple contexts, keep one canonical record and reference it from the relevant hubs. Prefer a relation/index update over moving the source. Completion can change the project’s lifecycle without invalidating its reusable insights.

Project-oriented organization and concept-oriented notes serve different retrieval needs. Keep project state near the project; connect reusable explanations across projects. On project completion, preserve the outcome, evidence, and reusable lessons, then archive only under the applicable policy/authorization.

## Distill progressively

Progressive summarization provides several reading depths: source → selected excerpts → key passages → concise synthesis → application. Add depth selectively on reuse, not as a compulsory processing pipeline. Plain text summaries can substitute for bold/highlight formatting.

For an agent editing a note:

1. Read the original evidence, not only an earlier AI summary.
2. Identify the question the condensed version should help answer.
3. Add a separately labeled takeaway; keep the original/pointer and useful detail accessible.
4. Check the condensed claims against the evidence. Preserve scope, uncertainty, exceptions, units, dates, and attribution that could alter the conclusion.
5. Mark an inaccessible source as unverified; do not make a polished summary appear independently checked.

Do not recursively compress summaries until their evidence disappears. Do not require a fixed word count, highlighting percentage, or all layers for all notes. The stopping condition is useful scanability with recoverable meaning.

## Develop and connect ideas

For a reusable concept, choose a title that names the idea, claim, or question, rather than a generic “Notes on X.” Cover one coherent idea with its essential reasoning and boundaries. “Atomic” is a reuse boundary, not a rule to create a file for each sentence. Preserve complete sources and event records; extract additional concept notes only when that aids use.

Before creating a concept note, search for the idea and its aliases. Extend an existing concept if the scope matches. If evidence contradicts it, record the disagreement or qualify the claim rather than silently overwriting history. A proposed relation is still a hypothesis until supported.

Read a target before linking it as support. Make the relationship explicit in prose: **supports**, **contradicts**, **qualifies**, **example of**, **applies to**, or **derived from**. These are descriptions, not mandatory schema fields. Do not link by shared keywords alone, fabricate targets, or optimize link counts. An isolated idea can stay in intake until a meaningful relation is found.

A **map of content (MOC)** is a curated navigation note for a question or cluster. Use one when finding or comparing scattered notes is becoming difficult. Group real links by purpose and add brief context or unresolved questions. Reuse an existing hub if it serves the purpose; do not create an empty map for every tag. A map points to knowledge and does not become proof of every claim it mentions.

## Express and reuse

Choose a concrete artifact that matches the request: a comparison table, design rationale, outline, draft section, checklist, example, or other usable component. Search for prior work before researching from zero. Small reusable outputs can be retained as intermediate work products even when the larger project is unfinished.

The agent-specific reuse check:

- Does the earlier material actually fit this audience, scope, and date?
- Which claims need current verification, and which are historical observations?
- Can the result retain source links without copying restricted material?
- What acceptance check makes this artifact usable now?

Mark incomplete outputs as drafts. After real feedback or use, capture a correction, outcome, or lesson when authorized; do not invent feedback or claim that the user learned an idea because the agent summarized it. Output preparation does not itself authorize publication, messaging, or scheduled follow-up.

## Review and learning

Honor the workspace’s cadence. If none exists, a weekly work review is a reasonable proposal; additional periodic checks depend on change rate and need. A suggested cadence is not a scheduled automation.

For a routine review, clarify the selected inbox batch, reconcile active project/task state, check waiting items and relevant dates, revisit deferred possibilities, and decide the next useful step. Consult calendars or task systems only if relevant and accessible. Keep applied changes separate from recommendations.

For knowledge maintenance, prioritize material whose failure would matter: claims about a changed product/version, superseded decisions, sources needed by active projects, repeatedly failed searches, and broken links. Age alone does not prove a note false. Revalidate a volatile claim before relying on it; do not refresh every note’s timestamp to make the workspace appear current.

Judge the system using small **observed samples**, not note count or graph density. During a requested review, try a few real questions such as “why was this decided?” or “what can we reuse?” Record whether the source was found, where search failed, whether an active project has an executable next action, and whether a note contributed to an actual output. Record timing or backlog age only if measured. Change the system where these observations show friction; avoid creating a measurement bureaucracy.

When the user’s goal is **learning or remembering**, offer a few recall/application questions, let the person answer before revealing the evidence, then give feedback. Space later practice according to their learning workflow. A readable archive is not evidence of human retention. Do not turn every reference note into a flashcard, require a quiz for a save request, or start reminders automatically.

## Worked example

Illustrative fixture, not a factual benchmark:

- **Capture:** “Pilot A completed in 4 days; pilot B in 9. Cohorts differ; investigate onboarding.” Keep the supplied experiment record/pointer and its dates, if known. Do not infer causation.
- **Organize:** Reference it from the active onboarding improvement project; reuse the same record in the experimentation hub if helpful.
- **Distill:** “The pilot durations differ; this observation alone cannot establish an onboarding effect.” Preserve the cohort caveat and original numbers.
- **Develop:** If justified, add a concept about comparing unlike cohorts, linked as a qualification of the pilot interpretation. Preserve the source record intact.
- **Express:** Produce the requested comparison or follow-up experiment brief; label the proposed action separately from an accepted decision.
- **Review:** Revisit after comparable measurements become available; correct the conclusion and affected output without deleting the original observation.
